# Выкат новой авторизации в прод — чек-лист для владельца

Пошаговая инструкция: что сделать, **зачем** и **как проверить**, в правильном порядке.
Идите сверху вниз, не перескакивайте. Отмечайте `[x]` по ходу.

Пометка **[Только владелец]** — шаг требует вашего входа в консоли (Vercel, Firebase, Google
Cloud, Upstash, Resend, регистратор домена). Ни ИИ, ни кто-то другой это сделать не может и не
должен: там ваши ключи.

Связанные документы: [перенос пользователей](migration-runbook.md) ·
[вход через Google](google-oauth-setup.md) · [контракт API](auth-api.md) ·
[ADR 001](adr/001-own-auth.md) · [план миграции](auth-migration-plan.md).

## Главные правила

- Секреты — **только** в Vercel → Project → Settings → Environment Variables. Не в код, не в git,
  не в чат, не в скриншоты. Секретные переменные отмечайте **Sensitive** (их потом нельзя
  посмотреть — только заменить; это и нужно).
- Файлы с ключами и выгрузками — **вне папки проекта** (например, `%TEMP%\bullbir-deploy`), и
  после использования удалять навсегда (Shift+Delete).
- **Никогда** не задавайте в Vercel переменные эмулятора: `FIRESTORE_EMULATOR_HOST`,
  `FIREBASE_AUTH_EMULATOR_HOST`, `FIREBASE_STORAGE_EMULATOR_HOST`, `VITE_USE_EMULATORS`.
  Сервер увидит их в боевой среде и откажется запускаться (так задумано — это защита).
- После любого изменения переменных в Vercel нужен **Redeploy** — старый деплой новых значений
  не видит.

Подготовьте папку один раз (PowerShell):

```powershell
New-Item -ItemType Directory -Force "$env:TEMP\bullbir-deploy"
```

## Этап A. До выката: пользователи «только телефон»

### A1. Посчитать их — пробный прогон переноса **[Только владелец]**

- **Зачем.** Новая система входит только по почте (пароль, код, Google). Кто входил только по
  телефону, после переезда не сможет войти (данные сохранятся, но доступа не будет).
- **Как.** Выгрузите пользователей и запустите анализ без записи — шаги 2 и 3 из
  [migration-runbook.md](migration-runbook.md):

  ```powershell
  firebase auth:export "$env:TEMP\bullbir-migration\firebase-auth-export.json" --format=json --project <ID-проекта>
  npm run migrate:users -- "$env:TEMP\bullbir-migration\firebase-auth-export.json" --offline
  ```

- **Как проверить.** В окне — количество «только телефон» (phone-only). Подробности (uid) — в
  приватном файле отчёта, путь к нему скрипт напечатает.

### A2. Решить, что с ними делать **[Только владелец]**

- **0 человек** — пропускайте шаг.
- **Несколько человек** — проще написать им лично (если знаете контакты) и попросить войти в
  текущий сайт и привязать почту до даты переезда.
- **Много** — выпустить заранее маленький релиз **старой** версии с баннером «привяжите почту»
  (этап 2b из плана), за 2–4 недели до переезда. Скажите — подготовлю отдельно.
- **Как проверить.** Повторный прогон A1 ближе к дате: число «только телефон» уменьшилось
  до приемлемого.

## Этап B. Аккаунты и ключи

Все переменные вводятся в **Vercel → Project → Settings → Environment Variables**.
Для каждой выберите окружение: **Production** (и **Preview**, если будете проверять превью —
см. этап E). Секреты отмечайте **Sensitive**.

Итоговый список (галочки — по мере добавления):

| Переменная | Секрет? | Шаг |
|---|---|---|
| `FIREBASE_PROJECT_ID` | нет | B1 |
| `FIREBASE_SERVICE_ACCOUNT_BASE64` | **да** | B1 |
| `FIREBASE_STORAGE_BUCKET` | нет | B1 |
| `AUTH_PEPPER` | **да** | B2 |
| `APP_ORIGINS` | нет | B3 |
| `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` | токен — **да** | B4 |
| `RESEND_API_KEY`, `MAIL_FROM` | ключ — **да** | B5 |
| `FIREBASE_HASH_SIGNER_KEY`, `FIREBASE_HASH_SALT_SEPARATOR`, `FIREBASE_HASH_ROUNDS`, `FIREBASE_HASH_MEM_COST` | signer key — **да** | B6 |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `OAUTH_REDIRECT_BASE` | secret — **да** | B7 |
| `VITE_FIREBASE_*` (6 штук) | нет | B8 |

### B1. Сервисный аккаунт для сервера **[Только владелец]**

- **Зачем.** Сервер через него выдаёт пропуск в Firestore (custom token), читает и пишет
  служебные коллекции, отзывает сессии Firebase и при удалении аккаунта стирает данные и аватар.
  Права — **минимальные**: если ключ утечёт, им нельзя будет сделать ничего лишнего.
- **Как.**
  1. Google Cloud Console (тот же проект, что у Firebase) → **IAM и администрирование →
     Service accounts → Create service account**. Имя: `bullbir-auth-server`.
  2. Роли (только эти):
     - **Firebase Authentication Admin**
     - **Cloud Datastore User**
     - Хранилище: лучше **не** давать роль на весь проект, а выдать **Storage Object Admin**
       только на бакет: Cloud Storage → Buckets → ваш бакет (`<проект>.firebasestorage.app`
       или `<проект>.appspot.com`) → **Permissions → Grant access** → почта сервисного аккаунта →
       роль Storage Object Admin.
  3. Сервисный аккаунт → **Keys → Add key → Create new key → JSON**. Сохраните файл в
     `%TEMP%\bullbir-deploy\sa.json` (не в папку проекта, не на синхронизируемый диск).
  4. Перекодируйте в base64 сразу в буфер обмена (на экран не выводится):

     ```powershell
     [Convert]::ToBase64String([IO.File]::ReadAllBytes("$env:TEMP\bullbir-deploy\sa.json")) | Set-Clipboard
     ```

  5. В Vercel: `FIREBASE_SERVICE_ACCOUNT_BASE64` = вставить из буфера, **Sensitive**.
  6. **Удалите JSON-файл навсегда:**

     ```powershell
     Remove-Item "$env:TEMP\bullbir-deploy\sa.json"
     ```

     и скопируйте в буфер что-нибудь другое, чтобы ключ не остался там.
  7. Ещё две переменные: `FIREBASE_PROJECT_ID` = ID проекта; `FIREBASE_STORAGE_BUCKET` = имя
     бакета без `gs://` (Firebase Console → Storage, вверху).
- **Как проверить.** В Google Cloud → IAM у сервисного аккаунта ровно эти роли; файла `sa.json`
  нигде нет; в Vercel переменная видна как Sensitive.

### B2. `AUTH_PEPPER` — серверный секрет **[Только владелец]**

- **Зачем.** Ключ, которым сервер «подписывает» одноразовые коды из писем (хранится не код, а
  его HMAC) и шифрует временную cookie входа через Google. Без него утёкшая база не даёт
  подобрать коды.
- **Как.** Сгенерируйте на своём компьютере:

  ```powershell
  node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
  ```

  Вставьте результат в Vercel как `AUTH_PEPPER`, **Sensitive**.
  **Разные значения** для Production и Preview (и третье — для своего `.env.local`): утечка с
  превью или с ноутбука не должна затрагивать прод.
- **Не меняйте после запуска без причины.** Смена pepper мгновенно делает недействительными
  все уже отправленные коды (регистрация, вход по коду, сброс пароля, смена почты) и прерывает
  входы через Google, начатые в эту минуту — люди увидят «неверный код» и будут запрашивать
  новый. Данные и пароли при этом не пострадают. Меняйте **только** если секрет утёк — тогда
  обязательно, и лучше в тихое время.
- **Как проверить.** Сервер не стартует, если pepper короче 32 байт или не base64 — смоук-тесты
  (этап E) покажут.

### B3. `APP_ORIGINS` — адрес сайта **[Только владелец]**

- **Зачем.** Сервер принимает изменяющие запросы только со своего сайта (защита от CSRF).
- **Как.** Точный адрес, с `https://`, без слэша и пути: `https://bullbir.app` (ваш домен).
  Если сайт открывается и с `www.` — добавьте оба через запятую:
  `https://bullbir.app,https://www.bullbir.app`.
- **Как проверить.** После деплоя вход работает; на чужом адресе запросы получают
  `origin_rejected` (403).

### B4. Upstash Redis — лимиты попыток **[Только владелец]**

- **Зачем.** Ограничивает перебор паролей и кодов (по IP и по аккаунту). Без него сервер в
  проде не запустится.
- **Как.** <https://console.upstash.com> → **Redis → Create database** → бесплатный тариф,
  регион ближе к функциям Vercel (по умолчанию Vercel — Washington, D.C., `us-east-1`). В
  разделе **REST API** скопируйте:
  - `UPSTASH_REDIS_REST_URL` (обычная переменная)
  - `UPSTASH_REDIS_REST_TOKEN` (**Sensitive**). Не берите «read-only token».
- **Как проверить.** Смоук-тест «5 неверных паролей» (этап E) даёт блокировку; в консоли
  Upstash растёт число команд.

### B5. Resend — отправка писем **[Только владелец]**

- **Зачем.** Через него уходят коды подтверждения, входа и сброса. Письма с непроверенного
  домена попадают в спам или не отправляются вовсе.
- **Как.**
  1. <https://resend.com> → **Domains → Add domain** → ваш домен (удобно поддомен, например
     `mail.bullbir.app`).
  2. Resend покажет DNS-записи — добавьте их **у регистратора домена / в DNS** (если домен
     подключён к Vercel DNS — в Vercel → Domains):
     - **SPF** (TXT и MX для поддомена отправки) — разрешает Resend отправлять от вашего имени;
     - **DKIM** (TXT `resend._domainkey…`) — подпись писем;
     - по желанию **DMARC** (TXT `_dmarc`) — улучшает доставку.
  3. Нажмите **Verify** и дождитесь статуса **Verified** (от минут до нескольких часов).
  4. **API Keys → Create API key**, права **Sending access**, только этот домен.
     В Vercel: `RESEND_API_KEY` (**Sensitive**).
  5. `MAIL_FROM` — отправитель на проверенном домене: `BullBir <no-reply@mail.bullbir.app>`.
- **Как проверить.** Домен в Resend — Verified; на смоук-тесте письмо приходит во «Входящие»,
  а не в спам (проверьте Gmail и ещё один почтовик).

### B6. Параметры старых паролей Firebase (`FIREBASE_HASH_*`) **[Только владелец]**

- **Зачем.** Чтобы перенесённые пользователи вошли **старым паролем** (сервер один раз сверит
  его со старым хэшем и сразу перехэширует в argon2id). Без этих переменных прод не запустится.
- **Как.** Шаг 1 в [migration-runbook.md](migration-runbook.md): Firebase Console →
  Authentication → Users → ⋮ → **Password hash parameters** → 4 значения.
  `FIREBASE_HASH_SIGNER_KEY` — **Sensitive**. Копируйте целиком, без пробелов и кавычек.
- **Как проверить.** Смоук-тест «вход старым паролем» (этап E) проходит.

### B7. Вход через Google **[Только владелец]**

- **Зачем.** Кнопка «Войти через Google». Необязательно: без ключей кнопка отвечает «временно
  недоступно», остальное работает.
- **Как.** Полная инструкция — [google-oauth-setup.md](google-oauth-setup.md). Для прода:
  1. В OAuth-клиенте (тип Web application) в **Authorized redirect URIs** добавьте **точно**:
     `https://<ваш-домен>/api/auth/oauth/google/callback`.
  2. **Секрет, который был вставлен в чат, считается утёкшим — перевыпустите его:** Google Cloud
     → Clients → ваш клиент → **Reset secret** (или Add secret, затем удалить старый). В Vercel
     кладите только **новый**.
  3. Переменные: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (**Sensitive**),
     `OAUTH_REDIRECT_BASE` = `https://<ваш-домен>` (должен входить в `APP_ORIGINS`).
  4. Экран согласия — статус **In production** (иначе войдут только test users).
- **Как проверить.** Смоук-тест «Google» проходит; ошибка `redirect_uri_mismatch` — адрес из
  п.1 не совпадает символ в символ.

### B8. Ключи клиента `VITE_FIREBASE_*` **[Только владелец]**

- **Зачем.** Браузерная часть подключается к Firestore/Storage. Это не секреты (они и так видны
  в коде сайта), но без них приложение не работает.
- **Как.** Firebase Console → Project settings → General → Your apps → SDK setup: `VITE_FIREBASE_API_KEY`,
  `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_STORAGE_BUCKET`,
  `VITE_FIREBASE_MESSAGING_SENDER_ID`, `VITE_FIREBASE_APP_ID` (скорее всего уже заданы в Vercel —
  проверьте).
- **Как проверить.** После входа открываются модули (задачи, дневник) и данные на месте.

**Проверка всего этапа B:** сравните список переменных в Vercel с таблицей выше; переменных
эмулятора и `NODE_ENV=development` там **нет**.

## Этап C. Firebase

### C1. Правила и индексы **[Только владелец]**

- **Зачем.** Новые правила закрывают служебные коллекции от браузера и проверяют claim `bb_ev`
  (почта подтверждена). Индекс нужен журналу безопасности. Правила из репозитория **сами не
  применяются**.
- **Как.** Из папки проекта:

  ```powershell
  firebase use <ID-проекта>
  firebase deploy --only firestore:rules,firestore:indexes,storage
  ```

- **Когда.** Вместе с деплоем кода (этап E, сразу после слияния). Новые правила рассчитаны на
  новый вход: старая версия сайта с ними будет видеть «нет доступа» к данным.
- **Как проверить.** Firebase Console → Firestore → Rules — дата публикации сегодняшняя;
  Indexes → индекс `security_events` (uid, at) в статусе **Enabled** (сборка — до нескольких минут).

### C2. TTL-политики (автоудаление просроченного) **[Только владелец]**

- **Зачем.** Коды, сессии, счётчики блокировок и журнал событий имеют срок `expiresAt`. Сервер
  сам не принимает просроченное, но удаляет его только TTL-политика Firestore. Без неё коллекции
  растут бесконечно (лишние деньги) и в базе остаются старые сведения об устройствах и IP дольше
  обещанных 180 дней.
- **Как.** Google Cloud Console → **Firestore → Time-to-live (TTL) → Create policy**, четыре раза:

  | Collection group | Timestamp field |
  |---|---|
  | `otp_codes` | `expiresAt` |
  | `sessions` | `expiresAt` |
  | `auth_throttle` | `expiresAt` |
  | `security_events` | `expiresAt` |

- **Как проверить.** Все четыре политики в статусе **Serving** (включение занимает время).
  Удаление происходит не мгновенно, обычно в течение суток после срока — это нормально.

### C3. Пользователей Firebase Auth не удалять

- **Зачем.** Через записи Firebase Auth работает мост к Firestore (тот же uid), и они нужны для
  отката. Решение из ADR: **не удаляем никогда**.

### C4. Выключение старых способов входа в Firebase Auth — **только в день переезда** **[Только владелец]**

- **Зачем.** После переезда старые входы Firebase (Email/Password, Phone, Google) не нужны —
  выключаем, чтобы через них никто не обошёл новую систему.
- **Когда.** **Только после** того, как новая версия в проде и смоук-тесты прошли (этап E).
  Если выключить раньше — **сломается живой сайт**: текущая версия входит именно через эти
  провайдеры, все пользователи окажутся снаружи.
- **Почему новой версии это не мешает.** Новая система входит в Firebase через custom token —
  этот способ работает при любых выключенных провайдерах.
- **Как.** Firebase Console → Authentication → **Sign-in method** → Email/Password, Phone,
  Google → **Disable**.
- **Как проверить.** Вход на сайте (пароль, код, Google) по-прежнему работает.

## Этап D. Перенос пользователей **[Только владелец]**

Подробно — [migration-runbook.md](migration-runbook.md), шаги 2–6. Кратко:

1. **Выгрузка** — только на своём компьютере, **вне папки проекта**
   (`%TEMP%\bullbir-migration`). Делайте её как можно ближе к деплою, чтобы попали все свежие
   регистрации.
2. **Пробный прогон** (`--offline`, затем dry run на боевой базе — только чтение). Проверьте
   отчёт: дубли почты, отключённые, «только телефон», пропущенные привязки Google.
3. **Запись** — с явным подтверждением `--apply --i-understand-production`.
4. **Сразу после деплоя** (этап E) повторите выгрузку и запись ещё раз: кто зарегистрировался
   в старой системе в промежутке, тоже перенесётся; уже перенесённые будут `exists`.
5. **Уборка:** удалить навсегда выгрузку, ключ миграции и файл отчёта; удалить сервисный
   аккаунт миграции в Google Cloud.

- **Как проверить.** Число `users_auth` с `importSource == "firebase-auth"` равно `imported`
  из отчёта; на смоук-тесте вход старым паролем работает.

## Этап E. Деплой

### E1. Слияние через Pull Request **[Только владелец — подтверждение]**

- **Как.** PR `feature/own-auth` → `main` на GitHub. Перед слиянием: зелёные проверки,
  `npm test`, `npm run typecheck`, `npm run lint`, `npm run build` — без ошибок.
- **Зачем PR.** Видно всё, что меняется, и есть одна точка для отката (`git revert`).

### E2. Превью Vercel (по желанию)

- Vercel сам соберёт превью для PR. Чтобы вход на нём работал, нужно:
  - переменные этапа B заданы и для окружения **Preview**;
  - адрес превью добавлен в `APP_ORIGINS` для Preview. Адрес у каждого деплоя свой; стабильный —
    адрес ветки вида `https://<проект>-git-feature-own-auth-<команда>.vercel.app`;
  - для Google — этот адрес отдельно добавлен в redirect URIs (маски Google не принимает).
- **Внимание:** если у превью те же Firebase-ключи, оно работает с **боевой базой**. Тестируйте
  только на тестовом аккаунте.
- **Проще:** пропустить превью и сразу после выката в прод пройти смоук-тесты (E3) — откат
  занимает минуту (этап F).

### E3. Выкат и смоук-тесты **[Только владелец]**

Порядок в день переезда: слить PR → дождаться деплоя → `firebase deploy` правил (C1) →
перенос (D, повторный прогон) → смоук-тесты → выключить провайдеры (C4).

Смоук-тесты на проде, на **тестовой почте** (лучше две разные):

- [ ] **Регистрация:** новая почта + пароль → приходит письмо с 6-значным кодом.
- [ ] **Код:** ввести код → попадаете в онбординг / приложение.
- [ ] **Вход паролем:** выйти и войти снова.
- [ ] **Старый пользователь:** вход старым паролем перенесённого аккаунта (своего).
- [ ] **Блокировка:** 5 раз неверный пароль → дальше «слишком много попыток», даже верный
      пароль не пускает.
- [ ] **Вход по коду во время блокировки:** «войти по коду» → код из письма → вход
      проходит, блокировка снята.
- [ ] **Google:** вход через Google.
- [ ] **Сброс пароля:** «забыли пароль» → код → новый пароль → вход новым паролем.
- [ ] **Смена почты:** в профиле → код на новую почту → на старую приходит уведомление.
- [ ] **Мои устройства:** войти со второго браузера/телефона → оба в списке; выйти на одном.
- [ ] **Выйти везде:** второй браузер после обновления страницы оказывается на экране входа.
- [ ] **Журнал безопасности:** события выше видны в профиле.
- [ ] **Удаление тестового аккаунта:** удалить → войти этой почтой нельзя, данных нет.
- [ ] **Логи без секретов:** Vercel → Project → **Logs** → фильтр `/api/auth`. В логах **не
      должно быть** паролей, кодов из писем, токенов, cookie. Есть `requestId` и коды ошибок —
      это нормально.

## Этап F. План отката

Если после выката что-то серьёзно сломано:

1. **Код.** Vercel → Project → **Deployments** → последний деплой **до** слияния → ⋮ →
   **Promote to Production** (откат за минуту). Потом спокойно `git revert` коммита слияния
   через PR.
2. **Правила.** Верните старые правила Firestore/Storage: Firebase Console → Firestore → Rules →
   History → предыдущая версия → Restore (то же для Storage). Либо `firebase deploy` из старого
   коммита.
3. **Firebase Auth.** Если провайдеры уже выключены — включите обратно Email/Password, Phone,
   Google (Sign-in method).
4. **Данные не трогаются:** `users/{uid}/...` одинаковы для старой и новой версии, записи
   Firebase Auth не удалялись.
5. **Учтите:** кто зарегистрировался или сменил пароль/почту **уже в новой системе**, в старой
   этого не увидит (новые аккаунты не войдут паролем, у сменивших — старый пароль). Им поможет
   «забыли пароль» в старой версии.

- **Как проверить.** Старый сайт открывается, вход старым паролем работает, данные на месте.

## Этап G. После запуска

- **Первые 1–2 недели:** раз в день смотрите Vercel Logs (ошибки 500) и журнал событий
  (всплески `login_failure`, `login_locked`).
- **Ход переноса паролей, раз в неделю:** Firestore → `users_auth` → фильтр `legacyPassword`
  `!=` `null` — записывайте число по датам; оно должно падать
  ([runbook, «Как понять, что всё идёт хорошо»](migration-runbook.md#как-понять-что-всё-идёт-хорошо)).
- **Ротация секретов** (новый ключ → Vercel → Redeploy → удалить старый):

  | Что | Когда |
  |---|---|
  | `GOOGLE_CLIENT_SECRET` | сразу (B7), дальше раз в год |
  | Ключ сервисного аккаунта | раз в 6–12 месяцев: создать новый ключ, обновить Vercel, удалить старый в Google Cloud |
  | `RESEND_API_KEY`, `UPSTASH_REDIS_REST_TOKEN` | раз в год |
  | `AUTH_PEPPER` | только при утечке (см. B2) |
  | Любой секрет | **немедленно**, если он попал в чат, скриншот, git или чужие руки |

- **Убрать `FIREBASE_HASH_*`:** когда число `legacyPassword` почти перестанет падать —
  назначить дату, стереть оставшиеся старые хэши и удалить переменные. Нужна небольшая правка
  кода (сейчас прод их требует) — см.
  [runbook, «Как закончить перенос»](migration-runbook.md#как-закончить-перенос-убрать-firebase_hash_).
- **Старый OAuth-клиент Firebase** (`…firebaseapp.com/__/auth/handler`) после переезда можно
  удалить в Google Cloud → Clients — он больше не используется.
