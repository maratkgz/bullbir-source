# Перенос пользователей из Firebase Auth (этап 3) — инструкция для владельца

Цель: перенести всех существующих пользователей в нашу систему входа **с теми же uid**, чтобы их
данные (`users/{uid}/...`) остались на месте. Пароли пользователей мы не знаем и не узнаем —
переносятся только их хэши (зашифрованные «отпечатки»).

Связанные документы: [план миграции](auth-migration-plan.md), [контракт API](auth-api.md),
[ADR 001](adr/001-own-auth.md).

## Главные правила безопасности

1. **Файл выгрузки и ключ сервисного аккаунта — вне папки проекта.** Папку проекта читают
   ИИ-инструменты, и её легко случайно закоммитить. Храните оба файла в отдельной папке во
   временной папке Windows, например `%TEMP%\bullbir-migration`, и **не** в синхронизируемых
   папках (OneDrive, Dropbox, Google Drive, «Рабочий стол»/«Документы», если они синхронизируются).
   Никогда не коммитьте, не пересылайте, не кладите в облако или мессенджер.
2. **После переноса — удалить навсегда** (Shift+Delete или очистить Корзину), см. шаг 6.
3. **`FIREBASE_HASH_SIGNER_KEY` — секрет.** Только в переменных окружения; в Vercel отметьте его
   как **Sensitive**. Не в код, не в чат, не в git.
4. **Ключ сервисного аккаунта — с минимальными правами** (только Firestore, роль
   «Cloud Datastore User») и удаляется в Google Cloud сразу после переноса.
5. **Записи в Firebase Auth не удаляем никогда** (решение из ADR).

Подготовьте папку один раз (PowerShell):

```powershell
New-Item -ItemType Directory -Force "$env:TEMP\bullbir-migration"
```

## Как это работает (коротко)

1. Скрипт `scripts/migrate-users.ts` (запуск: `npm run migrate:users -- <файл> ...`) читает
   файл-выгрузку и создаёт для каждого пользователя запись `users_auth/{uid}` (почта, «почта
   подтверждена», имя, способы входа) + индекс почты `auth_emails` + привязку Google в
   `auth_accounts`. Пароль у такой записи пока **старый** (`legacyPassword` — хэш Firebase),
   новый (`passwordHash`) пустой. Все такие записи помечены `importSource: "firebase-auth"`.
2. **Ленивая миграция пароля.** Когда человек первый раз входит в новую систему почтой и паролем:
   - сервер проверяет пароль по старому хэшу Firebase (алгоритм scrypt);
   - если пароль верный — сразу считает новый хэш argon2id, сохраняет его в `passwordHash` и
     **удаляет** `legacyPassword`;
   - со второго входа работает только новый хэш. Пользователь ничего не замечает.
3. **Почта не была подтверждена в Firebase.** Если пароль верный, но почта у перенесённого
   аккаунта не подтверждена, сервер **не** пускает сразу, а отвечает `email_unverified` и
   отправляет на почту 6-значный код. Приложение само показывает экран ввода кода.
   Когда владелец почты вводит код, аккаунт «очищается»: старый пароль и старые привязки
   (например, Google) **стираются**, все сессии завершаются, остаётся только пароль, который ввёл
   владелец почты. Это защищает от человека, который когда-то заранее зарегистрировал чужой адрес.
4. Кто ни разу не войдёт — так и останется со старым хэшем, пока мы его не сотрём (см. «Как
   закончить перенос»). Такие люди всегда смогут войти по коду на почту (этап 4) или сбросить
   пароль (этап 7).

## Кто переносится и кто нет

| Кто | Что происходит |
|---|---|
| Почта + пароль, почта подтверждена | Переносится. Первый вход старым паролем → пароль перехэшируется |
| Почта + пароль, почта **не** подтверждена | Переносится. При первом входе — код на почту (см. выше) |
| Вошедшие через **Google** | Учётка переносится. Привязка Google (`auth_accounts`) переносится **только** если почта аккаунта подтверждена **и** почта в Google совпадает с почтой аккаунта; иначе привязка пропускается (попадает в отчёт). Сам вход через Google — **этап 5**; до этого — по паролю (если был) или по коду на почту |
| **Только телефон** (без почты) | **Не переносятся.** По вашему решению им до переезда показывается просьба привязать почту (релиз 2b). Кто привязал — перенесётся при новой выгрузке |
| **Отключённые** (disabled) | **Пропускаются**, чтобы случайно не «включить» заблокированный аккаунт |
| **Дубли почты** (две учётки с одинаковой почтой без учёта регистра) | Пропускаются **обе** |

**Важно про дубли и отключённых:** пока вы их не разберёте, войти с этой почтой нельзя никому —
адрес считается занятым, потому что он всё ещё есть в Firebase Auth. Как разобрать:

- **Дубль почты.** Определите правильную учётку: у какой есть данные (Firestore →
  `users/{uid}`) и кто входил последним (Firebase Console → Authentication → Users, колонка
  «Signed in»). У **лишней** учётки смените почту в Firebase Console на служебную (например,
  `old-<uid>@invalid.example`) или отключите её. Учётки не удаляйте. Затем сделайте новую
  выгрузку и запустите скрипт снова — правильная учётка перенесётся, остальные будут `exists`.
- **Отключённый аккаунт.** Если отключён по ошибке — включите в Firebase Console, сделайте новую
  выгрузку и запустите скрипт снова. Если отключён намеренно — ничего не делайте: адрес останется
  занятым, это и нужно.

## Отчёт скрипта

- В окне скрипт показывает **только количества** (сколько готово, сколько пропущено и почему).
- Подробности о пропущенных (uid отключённых, «только телефон», дубли почты, пропущенные привязки
  Google) скрипт записывает в **приватный файл отчёта во временной папке системы** и печатает
  путь к нему. Откройте, разберитесь, затем удалите этот файл вместе с выгрузкой.
- Хэши, соли и полные почты скрипт **никогда** не печатает.

## Шаг 1. Параметры хэша паролей (нужны серверу)

1. Откройте [Firebase Console](https://console.firebase.google.com) → ваш проект →
   **Authentication** → вкладка **Users**.
2. Справа над таблицей нажмите **⋮** (три точки) → **Password hash parameters**.
3. Там 4 значения. Перенесите их в переменные окружения сервера (Vercel → Project → Settings →
   Environment Variables; локально — в `.env.local`, он не попадает в git):

   | В консоли | Переменная |
   |---|---|
   | `base64_signer_key` | `FIREBASE_HASH_SIGNER_KEY` (в Vercel — отметить **Sensitive**) |
   | `base64_salt_separator` | `FIREBASE_HASH_SALT_SEPARATOR` |
   | `rounds` | `FIREBASE_HASH_ROUNDS` |
   | `mem_cost` | `FIREBASE_HASH_MEM_COST` |

- В боевой среде (production) сервер **не запустится** без этих четырёх переменных — так
  ошибка видна сразу, а не при чьём-то входе. На эмуляторе они не обязательны (без них старые
  пароли просто не проверяются).
- Значения копируйте целиком, без пробелов и кавычек.

## Шаг 2. Выгрузка пользователей (только на вашем компьютере)

Нужен Firebase CLI (`npm i -g firebase-tools`) и вход (`firebase login`). Выгружайте сразу в
папку вне проекта:

```powershell
firebase auth:export "$env:TEMP\bullbir-migration\firebase-auth-export.json" --format=json --project <ID-вашего-проекта>
```

В файле есть почты и хэши паролей — **никому не пересылайте**.

## Шаг 3. Пробный прогон без записи (dry run)

По умолчанию скрипт **ничего не пишет** — только показывает отчёт. Нужен Node 22.18+ (у нас 24).
Команды запускаются из папки проекта, файл берётся по полному пути:

```powershell
npm run migrate:users -- "$env:TEMP\bullbir-migration\firebase-auth-export.json" --offline
```

(`--` после имени скрипта обязательно: всё, что после него, передаётся скрипту.)
`--offline` — только анализ файла, без базы. `--limit 10` — взять только первые 10 записей.
Смотрите количества в окне и подробности в файле отчёта (см. «Отчёт скрипта»).

## Шаг 4. Перенос на эмуляторе (безопасная репетиция)

`--apply` без флага `--i-understand-production` работает **только** на локальном эмуляторе
(задан `FIRESTORE_EMULATOR_HOST` с локальным адресом) и только с проектом, имя которого
начинается с `demo-`. Так случайно записать в боевую базу нельзя.

1. Запустите эмуляторы: `npm run emulators` (в отдельном окне).
2. В другом окне:

```powershell
$env:FIRESTORE_EMULATOR_HOST="127.0.0.1:8080"
npm run migrate:users -- "$env:TEMP\bullbir-migration\firebase-auth-export.json" --project demo-bullbir --apply
```

3. Запустите ту же команду ещё раз — все должны оказаться `exists` (повторный запуск ничего не
   ломает и не дублирует).
4. Запустите приложение на эмуляторе (`.env.local` с параметрами из шага 1) и войдите старым
   паролем → у пользователя `legacyPassword` исчезнет, появится `passwordHash`. Для учётки с
   неподтверждённой почтой появится экран кода; сам код печатается в окне dev-сервера строкой
   `[dev-mail]`.
5. **Сразу уберите переменную эмулятора** (иначе следующие запуски в этом окне молча уйдут в
   эмулятор):

```powershell
Remove-Item Env:FIRESTORE_EMULATOR_HOST
```

## Шаг 5. Перенос в боевую базу (только с явным подтверждением)

1. Создайте отдельный сервисный аккаунт **только для Firestore**: Google Cloud Console → IAM и
   администрирование → Service accounts → Create service account → роль **Cloud Datastore User**
   (больше никаких ролей) → Keys → Add key → JSON. Сохраните файл в
   `%TEMP%\bullbir-migration\` (не в папку проекта) и укажите путь:

```powershell
$env:GOOGLE_APPLICATION_CREDENTIALS="$env:TEMP\bullbir-migration\serviceAccount-prod.json"
```

   Убедитесь, что `FIRESTORE_EMULATOR_HOST` в этом окне **не** задан
   (`Test-Path Env:FIRESTORE_EMULATOR_HOST` должно вернуть `False`).
2. Сначала **dry run на боевой базе** (только чтение — покажет, кто уже есть, и конфликты):

```powershell
npm run migrate:users -- "$env:TEMP\bullbir-migration\firebase-auth-export.json" --project <ID-проекта>
```

3. Если отчёт в порядке — запись. Без флага `--i-understand-production` скрипт **откажется**
   писать в настоящий проект:

```powershell
npm run migrate:users -- "$env:TEMP\bullbir-migration\firebase-auth-export.json" --project <ID-проекта> --apply --i-understand-production
```

4. В конце — строка `Firestore results`: `imported` (перенесено), `exists` (уже были, пропущены),
   `email_taken` / `google_taken` (почта или Google уже заняты другим uid — разбираем вручную),
   `error` (ошибки сети — просто запустите ещё раз, перенесённые будут пропущены).

## Шаг 6. Уборка (сразу после переноса)

```powershell
Remove-Item Env:GOOGLE_APPLICATION_CREDENTIALS
Remove-Item Env:FIRESTORE_EMULATOR_HOST -ErrorAction SilentlyContinue
```

- Удалите **навсегда** (Shift+Delete или потом очистить Корзину) папку
  `%TEMP%\bullbir-migration` с выгрузкой и ключом, а также файл отчёта скрипта.
- Удалите ключ сервисного аккаунта в Google Cloud Console → IAM → Service accounts → ваш
  аккаунт → Keys (а лучше и сам этот сервисный аккаунт — он был нужен только для переноса).
- Записи в Firebase Auth **не удаляем** — они нужны мосту и как запасной вариант.

## Как понять, что всё идёт хорошо

- Сразу после импорта: число документов `users_auth` с `importSource == "firebase-auth"` равно
  `imported` из отчёта.
- Дальше раз в неделю смотрите, **сколько осталось пользователей со старым паролем**:
  Firebase Console → Firestore → `users_auth` → фильтр `legacyPassword` `!=` `null`. Это число
  должно со временем падать: каждый вошедший переходит на новый хэш. Записывайте цифры по датам.
- Жалобы «пароль не подходит» у многих сразу — почти всегда неверные параметры хэша (шаг 1).

## Как закончить перенос (убрать FIREBASE_HASH_*)

Старый хэш у тех, кто так и не вошёл, — это всё ещё хэш, который можно попытаться подобрать, если
утекут и база, и ключ. Поэтому у переноса должен быть конец:

1. Когда большинство активных пользователей перешли (число с `legacyPassword` почти перестало
   падать), **назначьте дату** окончания и при желании предупредите пользователей.
2. В эту дату: удалите `FIREBASE_HASH_*` из Vercel и **сотрите оставшиеся поля
   `legacyPassword`** (поставить `null`). Эти пользователи дальше входят по коду на почту или
   через сброс пароля — их данные никуда не денутся.
3. Сейчас сервер в production **требует** эти переменные, поэтому их удаление — отдельная
   маленькая правка кода (сделать их необязательными) плюс скрипт очистки. Скажите — подготовлю.
4. Аккаунты в Firebase Auth при этом **всё равно не удаляем**.

## Откат

- Скрипт только **создаёт** записи в `users_auth`, `auth_emails`, `auth_accounts`; данные
  пользователей (`users/{uid}/...`) и Firebase Auth он **не трогает**.
- Чтобы откатить перенос, удалите созданные документы: у них есть поле
  `importSource: "firebase-auth"` (Firestore → `users_auth` → фильтр по полю, либо удаление
  коллекций целиком, если новой системой ещё никто не пользовался). Удаляйте вместе
  соответствующие `auth_emails` и `auth_accounts`.
- Откат кода новой авторизации — через git (флагов «старый/новый вход» нет, см. ADR).
- Если кто-то уже вошёл и его пароль перехэширован — откату это не мешает: старый вход через
  Firebase Auth работает со старым паролем, Firebase мы не меняли.

## Частые вопросы

- **Пароль подходит в старом приложении, но не в новом.** Почти всегда — неверно скопированы
  параметры хэша (шаг 1). Проверьте все 4 значения, особенно `signer_key` целиком.
- **После ввода верного пароля просят код с почты.** Так и должно быть, если почта не была
  подтверждена в Firebase. Один раз ввести код — дальше обычный вход.
- **Человек не может войти и не может зарегистрироваться.** Скорее всего, его почта — дубль или
  отключённый аккаунт (см. «Кто переносится и кто нет»). Разберите вручную и перезапустите скрипт.
- **Пользователь входил только через Google.** Старого пароля у него нет — до этапа 5 он входит
  по коду на почту, потом через Google.
- **Можно запускать скрипт несколько раз?** Да. Уже перенесённые пропускаются (`exists`).

## Восстановление людей, удалённых из Firebase Auth (`scripts/relink-orphans.ts`)

**Когда нужно.** Если из Firebase Auth (консоль → Authentication → Users) были удалены
пользователи, а их данные в Firestore (`users/{uid}/...`) остались. Такой человек больше не может
войти: его старый вход удалён, а аккаунта в нашей системе у него нет. Скрипт находит такие
«осиротевшие» профили и создаёт для каждого аккаунт в нашей системе **с тем же uid** — человек
снова видит все свои данные.

**Что делает скрипт.**

- Перебирает документы `users/{uid}`. «Сирота» — профиль, у которого нет `users_auth/{uid}` и нет
  пользователя с этим uid в Firebase Auth. Адрес берётся из поля `email` профиля.
- Для каждого сироты создаёт `users_auth/{uid}` (почта **не подтверждена**, без пароля, без Google,
  `importSource: "orphan-relink"`) и `auth_emails/…`. Данные и профиль не трогает.
- Пропускает и пишет в отчёт: профили без почты или с неверной почтой; несколько сирот с одной
  почтой (пропускаются все); **конфликты** — почта уже занята другим аккаунтом в нашей системе или
  другим пользователем в Firebase Auth. Конфликты разбираются вручную.
- В консоль выводит только числа. Подробности (uid и почта — замаскированы) — в файле отчёта во
  временной папке; после разбора удалите его.
- Можно запускать сколько угодно раз: уже восстановленные пропускаются.

**Порядок.**

1. Репетиция на эмуляторе — как в шаге 4 (`npm run emulators` в другом окне; оба адреса
   эмулятора — и Firestore, и Auth):

```powershell
$env:FIRESTORE_EMULATOR_HOST="127.0.0.1:8080"
$env:FIREBASE_AUTH_EMULATOR_HOST="127.0.0.1:9099"
node scripts/relink-orphans.ts --project demo-bullbir            # проверка, без записи
node scripts/relink-orphans.ts --project demo-bullbir --apply    # запись в эмулятор
Remove-Item Env:FIRESTORE_EMULATOR_HOST, Env:FIREBASE_AUTH_EMULATOR_HOST
```

   Скрипт откажется работать, если задан только один из двух адресов эмулятора.

2. Боевая база — сначала **проверка без записи**. Нужен сервисный аккаунт, как в шаге 5, но с
   двумя ролями: **Cloud Datastore User** и **Firebase Authentication Viewer** (скрипт только
   читает Firebase Auth). Переменные эмулятора в этом окне должны быть **не** заданы.

```powershell
$env:GOOGLE_APPLICATION_CREDENTIALS="$env:TEMP\bullbir-migration\serviceAccount-prod.json"
node scripts/relink-orphans.ts --project <ID-проекта>
```

   Посмотрите числа: `Orphans found` (найдено сирот), `Would relink` (будет восстановлено),
   `Conflicts`, `Skipped`. Если что-то непонятно — откройте отчёт.

3. Запись. Без `--i-understand-production` скрипт **откажется** писать в настоящий проект:

```powershell
node scripts/relink-orphans.ts --project <ID-проекта> --apply --i-understand-production
```

   Одного человека: добавьте `--uid <uid>`. Попробовать на нескольких: `--limit 5`.

4. Уборка — как в шаге 6 (убрать `GOOGLE_APPLICATION_CREDENTIALS`, удалить ключ и отчёт).

**Что сказать этим людям.**

- Зайти на сайт и нажать **«Войти по коду из почты»**, ввести свою прежнюю почту и код из письма.
  Они попадут в свой старый аккаунт со всеми данными; почта при этом станет подтверждённой.
- После этого вход через Google снова работает (для адресов `@gmail.com`) — и попадает в тот же
  аккаунт. До входа по коду Google-вход будет отклонён (ошибка «аккаунт нельзя связать
  автоматически») — это защита, а не поломка.
- Пароль можно задать потом в настройках аккаунта.

**Важно: до переключения сайта на новую систему входа** эти люди **не должны** входить через Google
на старом сайте. Старый сайт создаст им в Firebase Auth **новый пустой uid** с той же почтой — и
тогда скрипт покажет конфликт («address used by another Firebase Auth user»), а человек окажется в
