# Перенос пользователей из Firebase Auth (этап 3) — инструкция для владельца

Цель: перенести всех существующих пользователей в нашу систему входа **с теми же uid**, чтобы их
данные (`users/{uid}/...`) остались на месте. Пароли пользователей мы не знаем и не узнаем —
переносятся только их хэши (зашифрованные «отпечатки»).

Связанные документы: [план миграции](auth-migration-plan.md), [ADR 001](adr/001-own-auth.md).

## Как это работает (коротко)

1. Скрипт `scripts/migrate-users.ts` читает файл-выгрузку пользователей и создаёт для каждого запись
   в `users_auth/{uid}` (почта, «почта подтверждена», имя, способы входа) + индекс почты
   `auth_emails` + привязку Google в `auth_accounts`. Пароль у такой записи пока **старый**
   (`legacyPassword` — хэш Firebase), новый (`passwordHash`) пустой.
2. **Ленивая миграция пароля.** Когда человек первый раз входит в новую систему почтой и паролем:
   - сервер проверяет пароль по старому хэшу Firebase (алгоритм scrypt);
   - если пароль верный — сразу считает новый хэш argon2id, сохраняет его в `passwordHash` и
     **удаляет** `legacyPassword`;
   - со второго входа работает только новый хэш. Пользователь ничего не замечает.
3. Кто ни разу не войдёт — так и останется со старым хэшем. Это не опасно: старый хэш без
   секретного ключа проекта бесполезен. Такие люди всегда могут войти по коду на почту или сбросить
   пароль.

Что **не** переносится:
- пользователи **без почты** (вход только по телефону) — скрипт их пропускает и выводит их uid.
  Для них заранее выходит релиз 2b («привяжите почту»);
- **отключённые** (disabled) аккаунты — пропускаются, чтобы случайно их не «включить»;
- **дубли почты** (две учётки с одинаковой почтой без учёта регистра) — пропускаются **обе**,
  скрипт показывает их uid. Решаем вручную.

## Шаг 1. Параметры хэша паролей (нужны серверу)

1. Откройте [Firebase Console](https://console.firebase.google.com) → ваш проект →
   **Authentication** → вкладка **Users**.
2. Справа над таблицей нажмите **⋮** (три точки) → **Password hash parameters**.
3. Там 4 значения. Перенесите их в переменные окружения сервера (Vercel → Project → Settings →
   Environment Variables; локально — в `.env.local`, он не попадает в git):

   | В консоли | Переменная |
   |---|---|
   | `base64_signer_key` | `FIREBASE_HASH_SIGNER_KEY` |
   | `base64_salt_separator` | `FIREBASE_HASH_SALT_SEPARATOR` |
   | `rounds` | `FIREBASE_HASH_ROUNDS` |
   | `mem_cost` | `FIREBASE_HASH_MEM_COST` |

> ⚠️ `signer_key` — **секрет**. Не присылайте его в чат, не вставляйте в код, не коммитьте.
> Только в переменные окружения.

## Шаг 2. Выгрузка пользователей (только на вашем компьютере)

Нужен Firebase CLI (`npm i -g firebase-tools`) и вход (`firebase login`). В папке проекта:

```bash
firebase auth:export firebase-auth-export.json --format=json --project <ID-вашего-проекта>
```

- Имя файла **обязательно** начинается с `firebase-auth-export` (или `auth-export`) — такие файлы
  уже в `.gitignore` и в git не попадут. Проверка: `git status` не должен показывать этот файл.
- В файле есть почты и хэши паролей — **никому не пересылайте**, не кладите в облако/мессенджер.
- После переноса файл удалите (шаг 6).

## Шаг 3. Пробный прогон без записи (dry run)

По умолчанию скрипт **ничего не пишет** — только показывает отчёт. Нужен Node 22.18+ или 24
(запускает `.ts` напрямую; на Node 22.6–22.17 добавьте `--experimental-strip-types` после `node`).

```bash
node scripts/migrate-users.ts firebase-auth-export.json --offline
```

`--offline` — только анализ файла, без базы. Что смотреть в отчёте:
- `Ready to import` — сколько будет перенесено;
- `Without email` — uid «только телефон» (их нужно было уговорить привязать почту в 2b);
- `Duplicate emails` — почты показаны маской (`a***@mail.com`), рядом uid. Решите вручную, какая
  учётка правильная;
- `--limit 10` — взять только первые 10 записей (для пробы).

Хэши, соли и полные почты скрипт **никогда** не печатает.

## Шаг 4. Перенос на эмуляторе (безопасная репетиция)

1. Запустите эмуляторы: `npm run emulators` (в отдельном окне).
2. В другом окне:

```bash
# PowerShell:
$env:FIRESTORE_EMULATOR_HOST="127.0.0.1:8080"; node scripts/migrate-users.ts firebase-auth-export.json --project demo-bullbir --apply
# bash:
FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 node scripts/migrate-users.ts firebase-auth-export.json --project demo-bullbir --apply
```

3. Запустите скрипт ещё раз с той же командой — все должны оказаться `exists` (значит, первый
   прогон записал всех, а повторный запуск ничего не ломает и не дублирует). Веб-интерфейс
   эмулятора в проекте выключен (`firebase.json` → `ui.enabled: false`).
4. Запустите приложение на эмуляторе и войдите старым паролем → в записи пользователя
   `legacyPassword` должен исчезнуть, появиться `passwordHash`.

## Шаг 5. Перенос в боевую базу (только с явным подтверждением)

1. Нужен ключ сервисного аккаунта (Firebase Console → Project settings → Service accounts →
   Generate new private key). Сохраните файл как `serviceAccount-prod.json` в папке проекта (такие
   имена в `.gitignore`) и укажите путь:
   PowerShell: `$env:GOOGLE_APPLICATION_CREDENTIALS="serviceAccount-prod.json"`.
2. Сначала **dry run на боевой базе** (только чтение — покажет, кто уже существует и конфликты):

```bash
node scripts/migrate-users.ts firebase-auth-export.json --project <ID-проекта>
```

3. Если отчёт в порядке — запись. Без флага `--i-understand-production` скрипт **откажется**
   писать в настоящий проект:

```bash
node scripts/migrate-users.ts firebase-auth-export.json --project <ID-проекта> --apply --i-understand-production
```

4. В конце — строка `Firestore results`: `imported` (перенесено), `exists` (уже были, пропущены),
   `email_taken` / `google_taken` (почта или Google уже заняты другим uid — разбираем вручную),
   `error` (ошибки сети — просто запустите ещё раз, перенесённые будут пропущены).

## Шаг 6. Уборка

- Удалите `firebase-auth-export.json` и ключ `serviceAccount-prod.json` с компьютера.
- Ключ сервисного аккаунта, созданный только для переноса, удалите в Google Cloud Console →
  IAM → Service accounts → Keys.
- Записи в Firebase Auth **не удаляем** (решение из ADR) — они нужны мосту и как запасной вариант.

## Откат

- Скрипт только **создаёт** записи в `users_auth`, `auth_emails`, `auth_accounts`; данные
  пользователей (`users/{uid}/...`) и Firebase Auth он **не трогает**.
- Чтобы откатить перенос, удалите созданные документы: у них есть поле
  `importSource: "firebase-auth"` (Firebase Console → Firestore → коллекция `users_auth` → фильтр
  по полю, либо удаление коллекций целиком, если новой системой ещё никто не пользовался).
  Удаляйте вместе соответствующие `auth_emails` и `auth_accounts`.
- Откат кода новой авторизации — через git (флагов «старый/новый вход» нет, см. ADR).
- Если кто-то уже вошёл и его пароль перехэширован — это не мешает откату: старый вход через
  Firebase Auth продолжает работать со старым паролем, Firebase мы не меняли.

## Частые вопросы

- **Пароль подходит в старом приложении, но не в новом.** Почти всегда — неверно скопированы
  параметры хэша (шаг 1). Проверьте все 4 значения, особенно `signer_key` целиком.
- **Пользователь входил только через Google.** У него нет старого пароля — он войдёт через Google
  (этап 5) или по коду на почту; привязка Google перенесена в `auth_accounts`.
- **Можно запускать скрипт несколько раз?** Да. Уже перенесённые пропускаются (`exists`).
