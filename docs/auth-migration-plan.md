# План миграции на собственную авторизацию

Связанное решение: [ADR 001](adr/001-own-auth.md). Работа идёт строго по этапам; после каждого —
отчёт, ручная проверка, зелёные тесты и **стоп до слова «дальше»**.

## Что есть сейчас (аудит)

| Что | Где | Судьба |
|---|---|---|
| Регистрация/вход почта+пароль | `AuthContext.register/login` (Firebase) | → `/api/auth/*`, этап 2 |
| Подтверждение почты | `sendEmailVerification`, экран `/verify-email` | → свой код на почту, этап 2 |
| Google | `signInWithPopup` | → OAuth 2.0 + PKCE на сервере, этап 5 |
| Телефон (SMS) | `signInWithPhoneNumber` + reCAPTCHA | **убираем**; заранее просим привязать почту (этап 2b) |
| Сброс пароля | `sendPasswordResetEmail` | → этап 7 |
| Смена пароля, удаление аккаунта | `Profile.jsx`, `Settings.jsx`, `firebase/account.js` | → этап 7 |
| Выход | `signOutAndClear` | → `/api/auth/logout` + очистка кэша, этап 2 |
| Гейт «почта подтверждена» в правилах | `request.auth.token.email_verified` | → claim `bb_ev` в custom token |

Интерфейс `useAuth()` (`user`, `profile`, `loading`, `isVerified`, `onboardingDone`, `register`,
`login`, `logout`…) **сохраняется**: экраны и модули менять не придётся, меняется только то, что
внутри провайдера.

## Аудит правил Firestore / Storage — найденные дыры

| # | Проблема | Риск | Исправление (этап) |
|---|---|---|---|
| R1 | Корневой `users/{uid}` клиент пишет **любыми полями**. Сейчас ролей там нет, но как только появится поле вроде `plan` или `role`, пользователь выдаст его себе сам | Средний (будущий) | Белый список полей через `diff().affectedKeys().hasOnly([...])` (этап 1) |
| R2 | Серверные коллекции (`users_auth`, `sessions`…) закрыты только общим «запретить всё» | Низкий сейчас, но легко сломать правкой | Явные блоки `allow read, write: if false` + тесты, что клиент их не прочитает (этап 1) |
| R3 | Гейт подтверждённой почты читает `email_verified` — у custom token его не будет | Сломает доступ после переезда | Claim `bb_ev` (этап 2) |
| R4 | Ветка «телефон без почты = подтверждён» | Станет лишней после отключения SMS | Удалить в этапе 9 |
| R5 | Аватар можно загрузить без подтверждённой почты | Низкий (спам в Storage) | Требовать `bb_ev` для записи (этап 2) |
| R6 | У правил нет ни одного теста | Любая правка может молча открыть данные | Тесты правил на эмуляторе (`@firebase/rules-unit-testing`), этап 1 |

Хорошее, что оставляем: изоляция `users/{uid}`, белый список коллекций, запрет SVG в аватарах
(SVG может содержать скрипт), админы назначаются только из консоли.

## Модель данных (только Admin SDK, клиенту закрыто)

```
users_auth/{uid}
  email            нормализованная (lowercase, trim, NFKC)
  emailVerified    boolean
  passwordHash     argon2id | null          (null — вход только по коду/Google)
  legacyPassword   { hash, salt } | null    (scrypt Firebase, удаляется после первого входа)
  status           'active' | 'locked'
  lockedUntil      timestamp | null
  passwordChangedAt, createdAt, updatedAt

auth_emails/{sha256(email)}       → { uid }  уникальность почты (создаётся в транзакции)
auth_accounts/{provider}:{sub}    → { uid, provider, email, linkedAt }   Google, потом Apple
sessions/{sha256(token)}          → { uid, createdAt, lastSeenAt, idleExpiresAt,
                                      absoluteExpiresAt, device (кратко из User-Agent), ipPrefix }
otp_codes/{id}                    → { purpose: verify|login|reset|change_email, emailHash, uid?,
                                      codeHmac, expiresAt (10 мин), attempts, usedAt }
security_events/{auto}            → { uid?, type, ipPrefix, device, at, meta }   без секретов
```

Ни одного секрета в открытом виде: токены сессий — SHA-256; коды — HMAC с серверным pepper;
пароли — argon2id; IP — только префикс (/24 для IPv4, /48 для IPv6). Просроченное чистится
TTL-политикой Firestore (включается в консоли — спрошу перед этим).

## API (одна функция-роутер `api/auth/[...route].ts`)

| Метод и путь | Этап | Что делает |
|---|---|---|
| `POST /register` | 2 | почта+пароль → письмо с кодом подтверждения, сессия |
| `POST /verify-email` | 2 | код из письма → `emailVerified=true` |
| `POST /login` | 2 | почта+пароль (+ ленивая миграция с этапа 3) |
| `POST /logout`, `POST /logout-all` | 2 | удаляют сессию / все сессии + `revokeRefreshTokens` |
| `GET /me` | 2 | кто я (без секретов) |
| `GET /sessions`, `DELETE /sessions/:id` | 2 | список устройств, выйти на одном |
| `POST /firebase-token` | 2 | custom token для моста (только по нашей сессии) |
| `POST /otp/request`, `POST /otp/verify` | 4 | вход по коду на почту |
| `GET /oauth/:provider/start`, `GET /oauth/:provider/callback` | 5 (6) | Google; Apple подключится тем же интерфейсом провайдера |
| `POST /password/reset-request`, `/password/reset-confirm` | 7 | сброс пароля |
| `POST /password/change`, `/email/change-request`, `/email/change-confirm` | 7 | смена пароля и почты |
| `DELETE /account` | 7 | удаление аккаунта со всеми данными |

Каждый запрос проходит общий конвейер: проверка Origin → лимит → zod-валидация → обработчик →
единый формат ошибок → лог без секретов.

**Apple без переделок:** OAuth сделан через интерфейс `OAuthProvider { authorizeUrl(), exchange(),
verifyIdToken() }`. Google — первая реализация; Apple добавится отдельным файлом + ключами в env.

## Лимиты (стартовые значения, обсуждаемо)

| Действие | По IP | По аккаунту / почте |
|---|---|---|
| Вход паролем | 20 / 10 мин | 5 ошибок → блок 15 мин, дальше удвоение до 24 ч |
| Запрос кода на почту | 10 / час | 3 / 15 мин |
| Ввод кода | 30 / 10 мин | 5 попыток на один код, потом код сгорает |
| Регистрация | 5 / час | — |
| Сброс пароля | 10 / час | 3 / час |

## Матрица «угроза → защита → тест»

| Угроза | Защита | Тест (Vitest + эмулятор) |
|---|---|---|
| Перебор паролей | лимиты IP + аккаунт, временная блокировка | 6-я ошибка → 429; после блокировки даже верный пароль не пускает |
| Узнать, есть ли почта | одинаковые ответы; фиктивная проверка argon2 для несуществующей почты | тела ответов идентичны; разница времени < порога на N замерах |
| Атака по времени | `crypto.timingSafeEqual` для хэшей и кодов | статическая проверка + тест на вызов |
| Утечка базы | только хэши/HMAC; в логах нет секретов | сканер логов в тестах ищет пароль/код/токен |
| Слабые и утёкшие пароли | ≥10 символов, HIBP k-anonymity (5 символов SHA-1) | мок HIBP: «утёкший» отклонён; HIBP недоступен → регистрация проходит + событие в журнал |
| CSRF | SameSite=Lax + проверка Origin на изменяющих запросах | POST с чужим Origin → 403 |
| Кража сессии | httpOnly cookie, `__Host-`, ротация при входе/смене пароля | старый токен после смены пароля → 401 |
| Повтор кода/ссылки | одноразовость (`usedAt` в транзакции), срок 10 мин | второй ввод того же кода → ошибка |
| Захват аккаунта через Google | привязка только если почта подтверждена у Google **и** у нас; state + PKCE + nonce | неподтверждённая почта → не привязывается; подменённый state/nonce → отказ |
| Доступ клиента к серверным коллекциям | правила `if false` | клиентский SDK на эмуляторе получает permission-denied |
| Открытая вкладка после «выйти везде» | `revokeRefreshTokens` + inMemory-мост | после logout-all выдача нового custom token невозможна |

## Порядок выката в прод (кратко)

1. Этап 2b в прод заранее → пользователи «только телефон» привязывают почту.
2. Прогон импорта в режиме dry run на боевой базе (только чтение) → отчёт → импорт по подтверждению
   ([migration-runbook.md](migration-runbook.md)).
3. Деплой новой авторизации. Все пользователи один раз входят заново.
4. 1–2 недели наблюдения по журналу событий.
5. Этап 9: удаление старого кода, выключение провайдеров в консоли. Записи в Firebase Auth не
   удаляем.

## Что я проверю на эмуляторе в этапе 1, прежде чем строить на этом

- Работает ли claim `bb_ev` в custom token и виден ли он в `request.auth.token` правил.
- `signInWithCustomToken` на существующий uid не меняет uid и данные.
- `@node-rs/argon2` собирается под Vercel (Node 20, x64) — прогон `vercel build` локально.
- Как именно `listUsers` Admin SDK отдаёт старые хэши паролей (нужно для этапа 3).
