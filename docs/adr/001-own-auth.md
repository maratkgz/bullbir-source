# ADR 001 — Собственная авторизация вместо Firebase Authentication

- **Статус:** предложено (ждёт подтверждения)
- **Дата:** 2026-11-25
- **Ветка:** `feature/own-auth` (от `feat/mandala-ai-security`)

## Контекст

Сейчас вход в BullBir целиком сделан на Firebase Authentication: почта+пароль, Google (popup),
телефон (SMS через reCAPTCHA). Сессия живёт в IndexedDB браузера в виде refresh-токена Firebase.

Мы хотим собственную систему входа:

- полный контроль над сессиями (список устройств, «выйти везде», сроки жизни);
- свои правила защиты (лимиты, блокировки, проверка утёкших паролей, журнал событий);
- одинаковый UX для всех способов входа, включая вход по коду на почту;
- опыт и портфолио: команда понимает, как устроена авторизация, а не только вызывает SDK.

Ограничения:

- данные пользователей лежат в Firestore под `users/{uid}`, и правила Firestore/Storage
  проверяют `request.auth.uid`. Терять uid и данные нельзя;
- хостинг — Vercel (статический фронт + Serverless Functions), бэкенда сейчас нет.

## Решение

1. **Своя авторизация — единственный способ входа.** Никаких флагов, переключателей и запасных
   режимов. Откат — только через git.
2. **Firebase Auth остаётся невидимым мостом к Firestore.** После успешного входа сервер через
   Firebase Admin SDK выдаёт custom token (`createCustomToken(uid, claims)`), клиент вызывает
   `signInWithCustomToken`. Так `request.auth` в правилах продолжает работать, а правила почти не
   меняются. Пользователь мост не видит: в интерфейсе нет ни одного экрана Firebase Auth.
3. **uid сохраняются.** Для существующего пользователя custom token выдаётся на его старый uid —
   все документы `users/{uid}/...` остаются на месте. Новые пользователи получают uid, который
   генерирует наш сервер (тот же формат: 28 символов base62).
4. **Сервер — Vercel Serverless Functions (TypeScript strict)** в `/api`. Все эндпоинты авторизации
   идут через **одну** функцию-роутер `api/auth/[...route].ts` (см. «Почему так» ниже).
5. **Данные авторизации — в Firestore, но только через Admin SDK**, в серверных коллекциях
   `users_auth`, `sessions`, `otp_codes`, `auth_accounts`, `security_events`. Клиенту правила
   запрещают к ним любой доступ.
6. **Сессия = случайный токен 32 байта** в cookie `__Host-session` (httpOnly, Secure,
   SameSite=Lax, Path=/). В базе хранится только SHA-256 от токена. Без активности — 7 дней,
   максимум — 30 дней. При входе и смене пароля — новый токен.
7. **Пароли — argon2id** (`@node-rs/argon2`), параметры OWASP (m=19 MiB, t=2, p=1).
   Коды из писем — HMAC-SHA256 с серверным секретом (pepper), а не голый хэш: 6 цифр перебираются
   за миллисекунды, если утечёт база без секрета.
8. **Защита от перебора — Upstash Redis** (`@upstash/ratelimit`), лимиты по IP и по аккаунту.
9. **Письма — Resend**; в разработке код печатается в консоль сервера.
10. **Миграция паролей — ленивая:** старые хэши Firebase (scrypt) импортируются в `users_auth`;
    при первом успешном входе пароль проверяется по старому хэшу и сразу перехэшируется в argon2id.

## Почему так (и почему не иначе)

**Почему мост через custom token, а не «выкинуть Firebase Auth целиком»?**
Правила Firestore и Storage умеют проверять только `request.auth` от Firebase. Без моста пришлось
бы перенести *все* чтения и записи данных (задачи, дневник, мандалы…) на свой сервер — это
переписать всё приложение и потерять офлайн-режим и real-time обновления Firestore. Мост стоит
~20 строк и сохраняет всё это.

**Почему одна функция-роутер, а не файл на каждый эндпоинт?**
На бесплатном тарифе Vercel в одном деплое не больше 12 Serverless Functions, а эндпоинтов у нас
~20. Один роутер также даёт одно место для общих вещей: проверки Origin (CSRF), лимитов,
обработки ошибок и логов — их невозможно «забыть» в новом эндпоинте.

**Почему сессия в своей cookie, а не только Firebase-токен?**
Firebase-токен живёт в JavaScript (IndexedDB) — его можно украсть через XSS. httpOnly-cookie
JavaScript не видит вообще. Плюс мы сами решаем сроки жизни и умеем отзывать сессии.

**Почему не JWT для сессии?**
JWT нельзя отозвать до истечения срока без отдельного «чёрного списка» — а тогда это та же база
сессий, только сложнее. Случайный токен + запись в базе отзывается одним удалением.

**Почему argon2id, а не bcrypt?**
Рекомендация OWASP 2024+: argon2id устойчив к перебору на GPU (требует память), у bcrypt лимит
72 байта на пароль.

## Важные детали моста (иначе будет дыра)

1. **Firebase-сессия в браузере не должна жить дольше нашей.** Клиент включает
   `inMemoryPersistence`: Firebase-вход живёт только пока открыта вкладка и при перезагрузке
   заново получается через `/api/auth/firebase-token` по нашей cookie.
2. **«Выйти везде» и смена пароля отзывают и мост:** сервер вызывает
   `auth.revokeRefreshTokens(uid)`. Иначе уже открытая вкладка на чужом устройстве продолжала бы
   читать Firestore до часа (срок ID-токена Firebase).
3. **Подтверждённость почты передаётся claim-ом в custom token** (`bb_ev: true`), а правила
   проверяют его вместо `email_verified`. Точное имя и поведение claim проверим тестом на
   эмуляторе в этапе 1, прежде чем на него полагаться.

## Последствия

**Плюсы:** полный контроль над входом и сессиями; httpOnly-сессии; единый журнал событий
безопасности; вход по коду на почту; данные и uid не трогаются.

**Минусы и риски — честно:**
- **Своя авторизация — это ответственность.** Firebase Auth годами тестировали тысячи людей;
  наши ошибки будут нашими. Снижаем риск: тест на каждый пункт защиты, разбор по OWASP ASVS в
  этапе 10, минимум собственной криптографии (только проверенные библиотеки).
- Появляется бэкенд, который надо обслуживать: секреты в Vercel, Upstash, Resend, ключ Admin SDK.
- Каждый запрос входа — холодный старт функции (~0,3–1 c в худшем случае).
- Все пользователи один раз войдут заново после релиза (решение владельца — без моста сессий).
- Пользователи, входившие только по телефону, должны заранее привязать почту — иначе потеряют
  доступ (данные сохранятся). Для этого нужен отдельный небольшой релиз *старой* версии заранее.
- Firebase Auth полностью не исчезает: остаётся пакет `firebase/auth` ради `signInWithCustomToken`
  и записи пользователей в Firebase Auth (их не удаляем — так решил владелец).

## Отклонённые варианты

| Вариант | Почему нет |
|---|---|
| Оставить Firebase Auth как есть | Не даёт контроля над сессиями и своим UX; цель проекта — своя авторизация |
| Готовый сервис (Auth0, Clerk, Supabase Auth) | Снова чужая авторизация + платный тариф при росте; не решает цель «своя система» |
| Перенести все данные на свой сервер и убрать Firebase Auth совсем | Переписать всё приложение, потерять офлайн и real-time Firestore |
| JWT-сессии без базы | Нельзя честно отозвать («выйти везде») |
| Флаг «старый/новый вход» | Две системы = вдвое больше поверхности атаки и багов; откат — через git |
